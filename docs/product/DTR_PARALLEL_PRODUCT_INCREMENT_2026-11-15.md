# DTR parallel product increment (2026-11-15)

Owner approved the parallel roadmap while SIBUR research continues. No live Data Platform, database, job schedule or operator runtime changes are part of this increment.

## Reliability slice

- A PostgreSQL session advisory lock (separate connection, retained across stage commits) fences execution of the same run; the isolated SQLite development path uses an in-process guard. This is not yet a distributed scheduler/profile-level admission lock.
- Scheduled recovery includes PENDING and interrupted RUNNING, alongside existing human/outcome states. Discovery retries use the original run date window. An intentional empty search requires `success_empty`; source failures are not no-results and remain visible in the run and digest, even with actionable cases. Explicit retry reuses existing completed items, not their processing calls. Mid-item recovery can still repeat an interrupted processing step; exactly-once external work is not claimed.
- Cross-run reuse requires equal frozen profile snapshots. All three relevant image recipes include the saved-profile directory; invalid path-like IDs are rejected.
- Mobile digest exposes run ID/state/stage and explicit discovery-incomplete flag without inventing a successful empty result for queued/old runs. Legacy digest completeness is unknown when not recorded. Existing decision and trading boundaries remain unchanged.

## Next slice: company boundary, then mobile client

`_find_duplicate_deal_id` in `src/modules/tender_intake/service.py` currently deduplicates procurement identity globally, including `Deal.procurement_number`; DTR and mobile human decisions refer to the canonical `deal_id`, and mobile portfolio/latest digest are not company-scoped. The DTR intake also hardcodes IT service direction/domain. Simply adding a Sionika search JSON would risk reusing a different company's deal, decision and classification. Do not enable a second company in unattended DTR until scoped lookup/write authorization, separate company-specific decision identity, source sharing policy, migration/backfill strategy and cross-company negative tests are designed and implemented. Reuse the existing company profile and SaaS tenant/role boundaries where appropriate; do not duplicate procurement documents or infer actual Sionika eligibility/costs. Scope shared public procurement facts separately from company-specific qualifications, decisions, commercial data and reports.

Then implement mobile client digest state and profile access using that same canonical contract, improve the existing single Operator Workspace, and run isolated acceptance. Do not activate production, APNs, live LLM, automatic submission or collection while research is in progress.

## Company-scoped portfolio foundation

The existing `PilotProject` / `ProcurementCase` entities already provide a company boundary. Reuse them through a dedicated `daily-tender-company-portfolio-v1` project per authenticated SaaS `customer_id`. The company API is under `/api/saas/company-portfolio/cases`; it uses existing SaaS feature, Bearer identity, subscription, member and legal gates. The same saved EIS registry number may belong to different companies, but case IDs and business decisions are separate. Saving a bare number is explicit manual reference selection only (`source_verified=false`), not source retrieval or eligibility verification. No duplicate procurement documents or global `Deal` creation occurs. Existing SaaS owned-run and company profile access paths remain unchanged.

Migration `108_company_portfolio_decisions` is additive: append-only decisions, tenant/member/case binding, expected revisions, idempotency and DEFER with timezone. Owners/admins may record decisions, analysts may save references, viewers read only. PostgreSQL row-lock serialization avoids stale concurrent writes; no external actions are taken. Existing records are not reclassified or copied; downgrade of populated decision history is prohibited. Separate temporary PostgreSQL tests established DTR advisory-lock persistence across commits, release on exception, actual migration upgrade, and concurrent decision conflict (one success, one 409, one row). The HTTP/SQLite tests cover independent company decisions, foreign case/history denial, role/consent, replay and history.

Scope limitation: the old owner-only Deal/DTR/mobile paths have NOT been switched to the company portfolio, nor has an actual company search profile been activated. Next bind tenant-owned qualification/report evidence and saved filter/profile context to scoped cases, then introduce an explicit authenticated mobile/web projection. Do not infer source verification or company eligibility from a saved registry number. No copied reports, customer data backfill, real Sionika tenant creation, commercial ETP activation, deployment or live scheduled runs in this increment.

## Company profile and original source binding

The tenant's existing `supplier_profile` fact is the sole source of search criteria, exposed read-only under `/api/saas/company-portfolio/search-context` with missing/active/expired state and version. This endpoint does not schedule searches. Migration 109 adds immutable references to the case, owned SaaS run, and exact profile fact version. The existing offline archive verifier checks saved ZIP/XML and attachment linkage/bytes before binding and again before evidence projection. Registry identity must match the case and the source must be supported 19-digit 44-FZ. The receipt's canonical digest is pinned; no copies of source files or private report data are made. Foreign case/run access is rejected before filesystem access. Superseded or expired profiles invalidate current assessment; explicit rebinding is required. Missing reports remain unavailable rather than producing invented assessments. Active evidence projects the existing report's cited facts and qualification for the authenticated company, with the qualification date and current (not frozen) report projection indicated; the report itself is not a signed, immutable result. Archived verification never establishes current legal status, signature validity, eligibility or authorization to submit. The new evidence endpoints require owner/admin/analyst and legal acknowledgment; search context contains criteria only. Existing global DTR and owner mobile remain separate. No live search, ETP collection, LLM, or actual tenant provisioning performed.

## Company cabinet web projection

Extend the existing authenticated `/saas` cabinet, not the owner-only global Operator Workspace, with the same company-case API as the iOS Companies tab. Portfolio paging, manual EIS reference save, versioned decision history, explicit GO/NO_GO/DEFER with a rationale, and evidence binding/verification all reuse the existing routes. A successful human decision is an internal portfolio event, not authorization to submit. The stale-revision response requires reopening and confirming again. An uncertain network result retains an in-memory idempotency key for the identical explicit retry. No browser token persistence or automatic legal acknowledgement is introduced. Session replacement/logout clears prior company profile inputs, references, file inputs, reports, and portfolio state; UI actions are serialized, and mismatched customer identities clear the session. Authentication/entitlement/role errors conservatively clear local session state. The browser script executes against isolated DOM and HTTP fixtures in Node; actual visual browser/device and production acceptance remain pending.

## Shared mobile and web decision contract

The native company client now records decisions through the same immutable company case API as the existing /saas web client. Expected revision and member identity are checked, explicit identical retries reuse an in-memory idempotency key, and a stale revision requires renewed human confirmation. Both surfaces read the authoritative latest decision on refresh; this provides canonical synchronization, not real-time push. No company-scoped automatic discovery or real case activation is part of this increment. HTTP regression with two authenticated members checks visibility across identities, replay scope, stale conflict and preservation of history; Swift request/response validation and unsigned test build pass. Browser and simulator end-to-end acceptance remain pending.
