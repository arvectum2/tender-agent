### Дополнительный семантический контроль отчёта как экспертного

Первоначальный настоящий отчёт для `software_modification` повторил **ошибочное утверждение**, будто следует получить проект контракта, хотя официальный `Прилoжение 5 Проект контракта.docx` прочитан целиком, его тип подтверждён `docKindInfo CP`. Предыдущее исправление предотвращало это только для `services` и не получало подтверждённый статус проекта из output orchestrator для другого режима.

Исправлено на общем уровне: `operator_output_orchestrator.py` передаёт в source-grounded `build_provisional_operator_recommendation` прямо вычисленное по разобранным документам `contract_draft_status`, без предположений модели. Для **любого** procurement scope отдельно различаются `present`, `parse_failed`, `absent`, `unknown`. При реально разобранном проекте программа рекомендует **изучить имеющийся контракт**, а не требовать его получения; все состояния сохраняют `manual_review_required` до решения оператора.

Повторная детерминированная проекция по настоящим сохранённым исходникам (**7 SHA неизменны**) подтвердила исправленный текст и статус `manual_review_required`. LLM **не перезапускался**, ошибочный оригинальный HTML и JSON сохранены как свидетельство. Приватный `contract_presence_reprojection.json` хранит булевы результаты и SHA новой рекомендации, не исходные длинные документы.

**Остающееся ограничение:** ряд рисков и вопросов модель сформулировала по-английски, хотя первичные закупочные документы и пользовательский отчёт русскоязычные. Они явно помечены `unverified_llm` / «Гипотеза LLM — проверить договор» и не являются подтверждёнными юридическими условиями.
