## Интеграционное последствие

Все три записи теперь имеют подтверждённую **первичным источником** категорию `PRICE_INFORMATION_REQUEST` — это запрос ценовой информации, предназначенный для сбора рыночных предложений. Их нельзя учитывать как три конкурентные закупки, которые можно выиграть подачей электронной заявки.

Официальный `getDocsIP` по всем трём номерам ранее повторно вернул `no_data`. Этот результат **не был доказательством отсутствия самой записи**: данные существуют, но в другом разделе ЕИС. Сохранённые `no_data` receipts остаются верными для конкретного метода, однако старое толкование «три пропавшие закупки» отклонено.

Для полноты регрессионной приёмки:
- **17** прежних кейсов — архивные извещения о закупках с предметными документами; это позитивный корпус для исходного конвейера.
- **3** подтвердившихся запроса цен — отдельный **негативный корпус** проверки маршрутизации, с `MARKET_RESEARCH_ONLY` вместо `GO/NO_GO` и без подачи заявки.
- Если DoD требует **20 реальных конкурентных закупок**, необходимо отдельно подобрать **ещё три** источниково подтверждённых конкурентных кейса. Нельзя автоматически считать этот набор «20 завершённых юридических экспертиз».

## Изменение Tender Agent

Добавлен чистый fail-closed helper `eis_price_request_guard.official_eis_price_request_source_error`. Он:
1. Сопоставляет только **официальный HTTPS-домен zakupki.gov.ru и путь /epz/pricereq/**, а не маску 19-значного номера.
2. Сравнивает `reestrNumber` либо `searchString` из официального URL с запрошенным номером, отклоняя несовпадение.
3. Возвращает `MARKET_RESEARCH_PRICE_REQUEST_ONLY`, блокируя handoff в конкурсный анализ **до SOAP/создания запуска**.
4. Не делает обратного небезопасного заключения «всякая карточка вне pricereq — точно конкурентная закупка».

**Все три карточки в момент просмотра имели «Завершен» как статус запроса цен.** Это не утверждение о наличии или отсутствии будущего конкурса либо текущем статусе иной закупки того же заказчика.
