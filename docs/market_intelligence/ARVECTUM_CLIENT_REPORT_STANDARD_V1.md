# ARVECTUM / MARKET INTELLIGENCE — стандарт клиентского отчёта v1.0

Дата: 30 октября 2026. Область: отчёты и презентации Power Quality в RU/EN, для дистрибьютора, производителя и иных заказчиков. **Применяется ко всем будущим релизам отчётов**, не только к текущему PDF.

## 1. Фирменные элементы

- Логотип: **только исходный Arvectum Block** (фирменный знак + название) из `src/modules/tender_operator_agent_demo/assets/arvectum-logo-block.svg`. Геометрию не менять. Подмена Unicode-символом, другим знаком, выдуманной монограммой, AI-логотипом запрещена. Допускается исключительно установка утверждённого цвета оригинального вектора.
- Цвета брендбука v2: Mint Primary `#00C8A0`, Deep Navy `#001432`, Mint Light `#78FAE6`, Graphite `#283246`, Soft Gray `#C8D2DC`, White `#FFFFFF`.
- Заголовки PT Sans Bold; текст PT Sans; технические значения, URL и ID — JetBrains Mono (при технической невозможности встраивания явно фиксировать и проверять моноширинный fallback). PDF включает встроенные шрифты.
- Сетка: 16:9, 960×540 pt, тёмный титул, светлые остальные слайды, один боковой заголовок и основная колонка. Логотип, поля и подвал одинаковы для всех слайдов.
- Запрещены скрытый текст, переполненные блоки, микрошрифты, слипшиеся таблицы и уменьшение текста вместо разбиения досье на две страницы.

## 2. Структура итогового отчёта

A0. Титул: адресат, продукт, период, дата среза.

A1. Методология и ключевые показатели: уникальные лоты, разные процедуры, ЕИС, подтверждённые договоры — отдельно. Один лот ≠ один договор.

A2. Сегментация предмета закупки: поставка, EPC/СМР, ПИР, сервис, мониторинг цен, компоненты, прочее; сумма сегментов = число лотов.

A3. Технологии и номинальное напряжение оборудования: УКРМ, БСК, SVC/СТК, STATCOM/SVG, фильтры и их сочетания. Не выводить номинал из класса ПС.

A4. Заказчики, конечные выгодоприобретатели и организаторы: разные роли, юридическое лицо с ИНН, корректная дедупликация.

A5. Годы и статусы: история *найденных* процедур; охват неполный, национальную динамику рынка не оценивать.

A6. Исходы процедур: объявление, рассмотрение, отмена, не состоялась, протокол, подписанный договор, исполнение/оплата; не смешивать.

A7. Финансы: НМЦ, предложение, договор, стоимость только PQ-оборудования, фактическая оплата — раздельно.

A8. Участники: заказчик, проектировщик, EPC, победитель, подписанный поставщик, OEM — не подменять ролями друг друга.

A9. Техническое соответствие и возможности FGI: по ТЗ, мощности, номиналу, климату, SCADA, гармоникам, допускам аналогов.

A10. Коммерческие приоритеты и следующие подтверждения.

A11. Источники, ограничения и условия использования.

После сводных слайдов: навигация по всем ID, индивидуальные досье, матрица пробелов, ссылка на machine-readable corpus snapshot.

## 3. Обязательные поля каждого досье (один канонический ID)

| Раздел | Поля, обязательные для отображения | Особые правила |
|---|---|---|
| Идентичность | Ключ notice:lot; ID процедуры; № лота; 44-ФЗ/223-ФЗ/коммерческий; ЭТП; дата источника; номер документа | Один юридический лот ровно один раз. Одна закупка может содержать несколько физических устройств |
| Заказчик | Покупатель, ИНН; корпоративный организатор; конечный пользователь / выгодоприобретатель; объект, регион | Организатор не становится покупателем автоматически |
| Предмет | Точная формулировка, короткое резюме; тип сделки: новая поставка / компонент / EPC / ПИР / сервис / ценовой запрос | Для EN показывать original RU subject отдельно от английского заголовка |
| Технические параметры | Технология; номинал **оборудования** (кВ); мощность (квар/Мвар); число устройств; модель; климат; SCADA и дополнительные требования | Номинал подстанции не доказывает номинал изделия |
| Финансы | НМЦ; предложение комиссии; цена заключённого договора; отдельно цена PQ-оборудования; отдельно оплата; НДС; валюта | Не складывать EPC с поставками, НМЦ — с ценами договоров |
| Участники | Победитель комиссии / ИНН; поставщик по договору / ИНН; EPC; проектировщик; OEM | Протокольный победитель ≠ договорной подписант ≠ изготовитель |
| Статус | Этап закупки, дата подтверждения; `unreviewed/approved/rejected` | Нельзя автоматически повышать зрелость по агрегатору |
| Доказательство | Официальный URL; тип источника, оригинальный SHA при наличии; внутренние ссылки на детальное evidence | Весь факт подтверждает **свой** оригинал, а не произвольный PDF в архиве |
| Пробелы | Явные неизвестные поля; приоритет следующей верификации | «Не установлено» не означает ноль или отсутствие события |

Поля **никогда не исчезают из шаблона**. Для неизвестных ставится «не установлено» / «not verified». Если таблица не помещается — делить досье на 1/2 и 2/2, не обрезать.

## 4. Оценка достоверности и очередь заполнения

A — официальный оригинал ЕИС/ЭТП, подписанный договор, исходный протокол, первичные вложения с SHA; судебный акт — только для прямо установленных фактов.

B — оригинальная открытая карточка площадки без полного комплекта документов.

C — агрегатор или вторичная перепечатка.

D — не подтверждённая исследовательская гипотеза.

Статус поля: `verified`, `reported`, `not_verified`, `not_applicable`, `conflict`. Обязательная оговорка: документ подтверждает не всё дело, а ровно изложенный в нём факт.

Порядок автономного дополнения корпуса:

- P0 — корректный ID лота, отсутствие дублей, номер и режим.
- P1 — оригиналы, заказчик с ИНН, конечный пользователь, даты и фактический статус.
- P2 — ТЗ и номинальные параметры изделия.
- P3 — протокол комиссии, победитель с ИНН.
- P4 — подписанный договор, цена и распределение по оборудованию/EPC/ПИР.
- P5 — изготовитель и исполнение/оплата по подтверждениям.

Приоритеты считаются **по каждому лоту** и публикуются отдельной матрицей completeness; замены неизвестных значений догадками запрещены.

## 5. Обязательная приёмка перед клиентом

- Досье соответствует каждому уникальному lot-ID в закреплённом срезе; есть явная дата и хеш исходного среза.
- Сводные таблицы точно согласованы с индивидуальными слайдами и не смешивают периоды или рублёвые типы.
- Настоящий Arvectum Block не перерисован; палитра и PT Sans сверены с брендбуком, оригинал логотипа прослеживается до source SVG.
- Заголовки, ссылки, технические поля и отсутствующие сведения не срезаются; проверяются Chrome DOM + геометрия PDF + выборочная визуальная приёмка длинных карточек.
- Изготовитель и подписант не «подтверждены» на основании одной протокольной заявки.
- RU/EN имеют идентичное покрытие корпуса. В EN технический русский первоисточник либо переведён после проверки, либо подписан «original Russian source wording».
- Генератор и проверка completeness — воспроизводимы в Git; каждый новый срез создаётся новым versioned файлом; предыдущие релизы не переписываются.
- Если хоть одно обязательное поле ещё не установлено — оно видно на слайде и в backlog; это **не блокирует выпуск предварительного отчёта**, но блокирует утверждение «все сделки полностью проверены».

## 6. Ответственность за актуальность

Единственный Watchdog Tender Agent продолжает искать первоисточники. Новый вводимый кейс немедленно попадает в canonical базу с уникальным ID и источником; генератор создаёт следующий versioned snapshot и синхронные отчёты. Любая правка старой подтверждённой карточки требует source-specific provenance и отдельной проверки, а не массового изменения по аналогии. Отчёт не «обновляется» подменой 115 на 117 на титуле.
