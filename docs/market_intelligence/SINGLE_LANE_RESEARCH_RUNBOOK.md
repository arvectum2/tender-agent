## Один запрос → один результат (S0–S11)

1. **S0**: профиль поставщика, его URL/документы, область, период, технологии. Пример `data/market_intelligence/supplier_profiles/fgi_power_quality.json`; offline `python -m src.modules.market_intelligence.supplier_brief --profile data/market_intelligence/supplier_profiles/fgi_power_quality.json`. Статус `UNVERIFIED` до проверки моделей по каталогу.
2. **S1–S2**: карта источников × месяцев × запросов: ЕИС 44-ФЗ, 223-ФЗ, реестры контрактов, коммерческие ЭТП (B2B-Center, Bidzaar, ЭТП ГПБ, ТЭК-Торг, РТС, Росэлторг, Фабрикант). Логировать URL, параметры, время, страницу/cursor, HTTP, повтор, ограничение доступа. Не превращать ошибку/403 в «нет закупок».
3. **S3–S5**: первичный оригинал, SHA-256, вложения, документ ТЗ, протокол; безопасная распаковка. Извлечение только через разрешённый интерфейс Data Platform, OCR/ChatGPT–ARC по проверенным пакетам; отказ 401 означает `blocked`, не обход.
4. **S6–S8**: семантическая релевантность **полного ТЗ**, в том числе в составе модернизации; валидация напряжения; разные роли `buyer / designer / EPC / bidder / OEM / supplier`. Устанавливать связи извещение → лот → проект → протокол → подписанный договор, а не агрегировать по совпадению слов.
5. **S9–S10**: раздельные поля `НМЦ / предложение / протокол / цена реестра / подписанная цена / цена PQ-компонента`, подтверждённые цитатами и SHA. Общий EPC-бюджет **не** равен объёму рынка оборудования. Только проверенные исходники, знаменатели, отрицательные доказательства и конфликтующие данные; пробелы не замещать оценками.
6. **S11**: `report.md`, `coverage.json`, `project_register.json`, `quality_report.json`, `verified-market-snapshot.json` из существующего приватного рабочего каталога с version/hash. Ясно различать `verified / provisional / unknown / excluded`. Готовый отчёт по доступной выборке ≠ полная перепись рынка; статус проекта `in_progress` до независимой приёмки DoD.
7. **Продолжение после прерывания**: проверить checkpoint, фактический HEAD, lease и retry eligibility; не повторять уже SHA-проверенные запросы; заниматься первичными источниками, а не декоративной перепиской roadmap; обновить *тот же* issue-комментарий и checkpoint с тестами и следующим точным действием.

## Фактическое состояние аудита

Активный Watchdog использует корпус **v29: 101 кандидат**, в том числе **34 лота 223-ФЗ = 33 уникальных извещения** и **67 коммерческих/нестандартных записей**. Оригиналы имеются по 31 из 33 уникальных 223-ФЗ извещений, два остаются с пробелами. Это *не* 101 подтверждённая покупка и *не* национальная статистика. Исторический MI-013 v20 (100 записей) и сторонний рабочий v40 (104) — отдельные версии с неустановленным полным dedup; переписывать текущую v29 нельзя. Последний Watchdog восстановил 32 оригинала по пяти процедурам, но **0 доказанных новых подписанных продаж оборудования PQ 6–35 кВ**.

Приоритеты: официальные итоги/подписанты и роли; оригиналы коммерческих ЭТП; восстановление пробелов 2024–2026; dedup v20/v29/v40 с исходными SHA; 15 ожидающих Data Platform SDK файлов после разрешения авторизации; затем полный проверяемый пользовательский отчёт. FGI — профиль *искомого соответствия*, а не автоматически участник российских закупок.

## Граница с другими проектами

Tender Agent владеет онтологией закупок, графом проектов, ролями, ценами, верификацией и отчётом. Data Platform владеет общими загрузчиками, извлечением/индексами по утверждённому SDK. Procurement LLM — отдельное обучение/оценка, только после права использования данных, экспертной разметки и независимой проверки; никаких «gold» из сырых машинных выводов.

Слияние в `main` — только после актуального зелёного CI, дифф-ревью, применимых Company AM-4 разрешений и проверки источников. Без force merge, действий с тендерными заявками, production или секретами.
