# Tender Agent — переход от LLM-пересказа к исследованию первоисточников

**Архитектурная задача TA-FULL-CORPUS-RESEARCH-20261014, этап 1.** Работы ведутся в `arvectum2/tender-agent`, в отдельной draft-ветке поверх PR #425. Никаких заявок, подписей, Production и платных API.

## Почему предыдущий подход не работает

Независимая проверка закупки музея Хлеба №0372200172326000015 показала две разные причины ложных выводов:

1. Старый управляемый LLM видит лишь сокращённый набор из трёх ролей (извещение/ТЗ/договор), около 8–21% исходного текста. Приложения и отдельные пунктовые исключения могут вообще не попасть во вход модели.
2. Даже с расширенным релевантным контекстом Gemma4 12B в формате `PASSED` назвала обязательный допуск **только СМП/СОНКО** предпочтением, общие технические требования — официальными критериями оценки, а пункт §3.8 о разрешённом изменении цены/объёма ±10% — фиксацией цены.

Следствие: **пройденный JSON schema test не означает достоверности закупочного анализа**. Дополнять промпт отдельными ключевыми словами или без проверки принимать ответы другой модели недостаточно.

## Целевая архитектура

```text
Поиск процедуры (44-ФЗ / 223-ФЗ / коммерческие площадки)
  ↓ оригинальный ID, площадка, версия, срок, SHA-файлов
Реестр всех полученных файлов (включая приложения)
  ↓ полнота, безопасное извлечение, OCR/таблицы, ошибки чтения
Нормализованный корпус + неизменяемые исходники + SHA
  ↓ поиск по исследовательским вопросам И ПО ВСЕМ документам
Реестр доказательств: файл → точный диапазон → цитата → SHA
  ↓ отдельное извлечение точных структурированных фактов из XML/таблиц
Многошаговый анализ LLM (вопрос → найденные цитаты → гипотеза)
  ↓ независимая проверка исходных фрагментов / оговорок / конфликтов
Проверяемые утверждения: SUPPORTED / CONTRADICTED / UNKNOWN
  ↓ полнота вопросов, критерии допуска, экономика и бюджет
Согласованный отчёт + ручная проверка и решение человека
```

### Этап 1 — реализовано в этой ветке

- `full_corpus_research.py`: все извлечённые физические документы независимо от роли, точный `file_id`, `role`, `source_sha256`, статус каждого файла, без молчаливого обрезания данных. Сверхлимитные/непрочитанные файлы отмечаются незавершёнными, а не исчезают.
- Многосторонний поиск по 15 темам: идентичность, НМЦК, сроки, допуск, оценка, обеспечение, предмет, функционал, приёмка, оплата, изменение цены, права, гарантия, ответственность, сроки исполнения. Новые исследовательские вопросы задаются как данные, без переписывания поискового движка.
- У каждого совпадения есть **исходный документ, SHA-256 всего нормализованного текста, точный символьный диапазон, точная исходная цитата и её SHA-256**. Поисковое совпадение не равно доказанному смыслу; поле `semantic_status=UNVERIFIED_CONTEXT_ONLY`.
- Приоритет официального XML для цены/сроков и обязательное разнообразие исходных ролей (извещение и договор). Если найдено несколько извещений — `MULTIPLE_NOTICE_REVISIONS_REVIEW`; нельзя молча считать последнее по порядку файлом последней редакции.
- Точные источникоопределённые сведения ЕИС `nmck`, `submission_deadline`, `publication_date`, `procurement_subject` извлекаются **существующим XML-парсером** только при однозначном номере реестра и безопасном XML. Статус `ORIGINAL_XML_EXTRACTED_NOT_CURRENT_ATTESTED` намеренно не удостоверяет актуальность.
- Сводка около 10 тыс. символов составляется из результатов поиска **по всем файлам**, отдельно от прежних сокращённых входов. Каждая LLM-секция получает источник с маркировкой `HUMAN CHECK REQUIRED`.
- Внешний неизменённый AST-locked R3-оркестратор не изменяется: интеграция через явное внедрение зависимостей в legacy facade. Метаданные `source_research` и `source_research_llm_claims` попадают в отчётные outputs; любые утверждения модели остаются `semantic_verification=NOT_PERFORMED`.
- UI/отчёт получают явные ограничения по неполным текстам, отсутствующим темам и невозможности признать schema PASS юридической проверкой. Автоматическая подача, письма, подписи и GO не добавлены.

### Этапы 2–5 — НЕ закрыты текущим PR

2. **Индексация на уровне пунктов и таблиц:** страница PDF/номер таблицы/пункт договора, OCR-качество, версии приложений, правила приоритетности исправленных редакций. Сейчас диапазоны точны по нормализованному тексту, но не равны номерам страниц оригинала.
3. **Семантический верификатор утверждений:** модель должна выдавать атомарные утверждения с точными цитатами; независимый verifier проверяет подразумеваемые исключения, цифры, отрицания и конфликтующие пункты. Проверка наличия слов никогда не должна повышать статус до `SUPPORTED`.
4. **Эталонные тестовые комплекты:** обезличенная коллекция 44-ФЗ, 223-ФЗ, коммерческих конкурсов и негативные испытания на ложный допуск, цену, сроки, обеспечительные меры, версии документов, критерии оценки и исключительные права. Целевые acceptance-метрики нужно считать на проверенной человеком выборке, а не объявлять «98% точности» без измерений.
5. **Полная пользовательская приёмка:** отображение каждого решения с открытием точного источника, матрица неохваченных пунктов/файлов, разблокировка только после подтверждения официальной редакции ЕИС, коммерческой и юридической проверки владельцем.

## Критерии добросовестности

- Если хотя бы один файл не извлечён, утверждение о *полноте* анализа запрещено.
- Если найдено несколько версий одного извещения, свежесть не выводится из порядка загрузки и рассматривается как неопределённость до проверки официальной редакции.
- Если LLM ссылается на пункт, этого недостаточно: доказательство должно иметь идентификатор оригинального документа, хеш, точную цитату, поддержку смысловой проверки и состояние ревизии.
- Отсутствие результатов поиска нельзя переводить в «требований нет».
- Статусы `PASSED JSON`, `SOURCE_CONTEXT_FOUND_REVIEW` и `SEMANTICALLY_VERIFIED` принципиально различны.
- Итоговая рекомендация остаётся `MANUAL_REVIEW_REQUIRED`, пока все обязательные проверки не закрыты.

## Проверка на реальном корпусе

Сохранённая архивная закупка Музея Хлеба: **6/6 нормализованных документов** и **15 тем** обработаны, `unread_file_ids=[]`; независимо проверены исходные SHA-256 файлов из предыдущего этапа QA. Найдены XML `maxPrice` и `endDT`, ограничения допуска, обеспечение 10%, билетная функция, права, изменение цены. Это **проверка покрытия источников и транспорта исследования**, а не подтверждённый юридический/финансовый GO. Любые модельные ответы проверяются отдельно.

Новых контактов с заказчиком, действий на ЭТП и изменений в private/production системах не выполнялось.


## Результат LLM-исследования полного корпуса (реальный прогон)

Mac mini, Gemma 4 12B через localhost, архивная закупка музея Хлеба. Вход: 6/6 извлечённых файлов, 15 полнотекстовых тем, отдельные фрагменты с хешами плюс традиционные контексты трёх ролей. Запуск выполнялся **406,2 секунды**, `4/4 validation_status=PASSED`, каждая секция `needs_human_review`. Сырые ответы сохранены **только локально**, в private temp JSON с правами 0600.

**Проверка смысла против оригиналов: FAILED.**

- Запись `qualification_requirements` вновь содержит «Preference given» вместо ограничения только СМП/СОНКО.
- `evaluation_criteria` по-прежнему подменяет официальную систему оценки качественными свойствами будущего сайта.
- Разбор `3.8. Price Adjustment` неверен: модель утверждает изменение цены без изменения объёма и вводит ограничение штрафов, хотя пункт 3.8 предусматривает изменение объёма до ±10% и пропорциональную корректировку цены, а ограничение штрафов — отдельный вопрос.
- Структурно выделенные исходным XML `nmck=1000000` и `submission_deadline=16.10.2026 10:00+03:00` снова отсутствуют в свободном резюме.
- Сохранены и некоторые правильные пункты: 3 концепции, SEO, билетные сервисы, адаптация для слабовидящих, исключительные права, аванс/обеспечение, срок завершения 7 декабря, риск задержки бюджетного финансирования.

**Вывод:** успешное извлечение первоисточников и подача верных фактов на вход не делают самостоятельный ответ модели достоверным. Все исходные XML-поля должны отображаться отдельно от генерации LLM; юридические и коммерческие утверждения модели обязаны пройти отдельную проверку с правом на UNKNOWN. Текущий PR реализует поиск источников и реестр доказательств как основу этой схемы, **но не завершает семантический верификатор**.


## Системные исправления сверх первичного полнотекстового поиска

### Привязка к нумерованным пунктам

Модуль `full_corpus_clause_review.py` извлекает нумерованные пункты из полного нормализованного текста договора и ТЗ с исходными диапазонами и хешами. Для утверждений LLM с номером пункта проводится отдельный поиск ссылки: `CLAUSE_LOCATED_NOT_SEMANTICALLY_VERIFIED`, `CLAUSE_NOT_FOUND`, `AMBIGUOUS_CLAUSE_REFERENCE` или `NO_NUMBERED_CLAUSE_REFERENCE`.

На реальном сохранённом комплекте Музея хлеба найдено **236 нумерованных пунктов**. Для §3.8 найден исходный пункт договора с прямым текстом об изменении объёма/цены; §2.4.15 об исключительных правах также обнаружен. Пункт 2.2.3.6.5 о доступности повторяется в ТЗ и приложении к договору и потому помечается **неоднозначным**, пока редакция документа не разрешена. **Сам факт нахождения пункта не доказывает правильности пересказа модели.**

### Устранение принудительной фабрикации в JSON-схеме

Предыдущая Pydantic-схема `LLMTenderOperatorRequirementsDraft` требовала **хотя бы один** элемент `evaluation_criteria` и `qualification_requirements`, даже когда в оригинальной процедуре нет доказанного отдельного порядка оценки или квалификационного условия. Такой контракт системно заставляет LLM заполнять недоказанные поля. Теперь списки остаются обязательными ключами JSON, но **могут быть пустыми**. Аналогично модель может вернуть `contract_risks=[]`, если ни один риск не привязан к доказательству, вместо выдуманного номера пункта.

В новой версии prompt assets `tender-operator-requirements-source-v2` и `tender-operator-contract-risk-source-v2` явно требуется различать **официальную оценку заявок** и технические свойства результата, ограничение «только СМП/СОНКО» и предпочтение, указывать точный источник и исключения, отказываться от выдуманных критериев/пунктов. Новые ключи исключают молчаливое повторное использование старых сохранённых v1-схем. Однако даже правильный prompt не удостоверяет LLM-вывод автоматически.

### Статус полноценного решения

Основа источникоориентированного исследования внедрена. **Независимый семантический verifier, эталоны и полная постраничная сегментация ещё не готовы**; до их проверки `HUMAN_REVIEW_REQUIRED` остаётся обязательным. Зафиксирована разница между `SOURCE_CLAUSE_LOCATED`, `CONTRADICTION_FOUND`, `SEMANTICALLY_VERIFIED` и `NOT_VERIFIED`; пока система не выдаёт статус `SEMANTICALLY_VERIFIED` автоматически.


## Вторая модельная проверка и независимый контроль противоречий

На Mac mini повторены **две наиболее проблемные секции** Gemma4 12B (`requirements` и `contract_risk_memo`) с обновлённой необязательностью содержимого списков, source-v2 prompt assets, полнотекстовым индексом всех 6 документов и источниковыми полями XML. Реальный runtime **186,0 секунды**, обе секции `PASSED` по JSON, обе `needs_human_review`. Приватный ответ остаётся в локальном каталоге с правами 0600.

Прогон v2 исправил три наблюдаемых ошибки: (1) включил в резюме архивные факты `НМЦК=1 000 000 ₽`, `подача до 16.10.2026 10:00+03:00`; (2) вернул `evaluation_criteria=[]` вместо вымышленных критериев оценки; (3) верно сообщил, что §3.8 разрешает изменение объёма и соответствующую корректировку цены. **Но допуск СМП/СОНКО снова назван предпочтением**, хотя оригинал содержит слова «которыми могут быть только субъекты малого предпринимательства, социально ориентированные некоммерческие организации».

Для исправления класса ошибок создан `full_corpus_modality_audit.py`: независимый **отрицательный** проверяющий, который ищет исходные модальности (ограничение только определёнными участниками, разрешение изменения объёма/цены по соглашению сторон) и сверяет их с утверждениями модели. На исторических фактических ответах результаты воспроизводятся:

| Реальная версия Gemma | Фактологических противоречий с модальностью оригинала |
|---|---:|
| Полный корпус + исходная LLM-схема | 2: участники «preference» вместо «only»; §3.8 описан как изменение цены без изменения объёма |
| Полный корпус + source-v2 schema/prompts | 1: участники «preference» вместо «only» |

Проверяющий возвращает `CONTRADICTED_BY_EXCLUSIVE_SOURCE` / `CONTRADICTED_BY_SCOPE_ADJUSTMENT_CLAUSE` с exact-source span и SHA. Для оставшихся содержательно похожих утверждений он возвращает только `SOURCE_MODALITY_PRESENT_SEMANTICS_UNVERIFIED` либо `SOURCE_PRICE_CHANGE_PRESENT_SEMANTICS_UNVERIFIED` — **это не положительная проверка правильности**. Если есть противоречие, в `source_research_quality_gate` выдаётся `CONTRADICTION_REVIEW_REQUIRED`, `bid_ready=false`, `claim_semantics_verified=false`, независимо от `PASSED` структуры модели. При неполном корпусе статус `CORPUS_INCOMPLETE` имеет высший приоритет.

### Проверка неизменности документов

Реестр учитывает различие между `text_sha256` полного нормализованного текста и `raw_sha256` исходных байтов. Если manifest содержит конкретный ожидаемый SHA-256, полный индекс не принимает документ с неправильным/невалидным SHA, отсутствующими исходными байтами или дублирующимся ID: статусы `HASH_MISMATCH_UNREVIEWED`, `INVALID_SHA_RECEIPT_UNREVIEWED`, `DUPLICATE_MANIFEST_ID_UNREVIEWED` и `DUPLICATE_SOURCE_ID_UNREVIEWED`, без использования текста в поиске и в LLM evidence brief. Если внешнего ожидаемого хеша нет, документ получает самовычисленный digest с `NO_DECLARED_DIGEST`, но **не объявляется независимо проверенным** (`source_truth_attested=false`).

Итог последнего локального прогона по исходникам и новым негативным тестам: **111 focused pytest PASS, Ruff PASS, git diff --check PASS**, повторный контроль 6/6 архивных документов и прежних ошибок модели 2→1. Этот результат подтверждает функциональность исследовательского шлюза, но **не** полную экспертную семантическую экспертизу любой произвольной документации. Дальнейшие обязательные работы: таблицы/страницы/точные редакции, более общий верификатор смысловых утверждений и независимая human-gold оценка для 44-ФЗ, 223-ФЗ и коммерческих процедур.
