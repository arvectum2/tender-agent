# Source adapter contract — stage 1

Separate discovery from detail capture, attachment recovery, parsing, indexing and outcome interpretation. Each stage uses its own bounded queue and reconciliation receipt. A source may have a working parser but no authorization or verified operational access; catalog entry alone never activates a connector.

The initial catalog is a pure contract, not an executable scheduler. Evidence levels describe existing implementation/pilot observations, not live uptime, complete coverage or permission. EIS 44-FZ/223-FZ/capital repair use separate logical namespaces; ETP GPB etp/gos/price_request/etp_click/sale have distinct identities; sale is observation-only, never procurement demand. GEH is a customer scope of GPB, not a separate platform. SIBUR procedure is a logical namespace for established registry IDs. MOS public auction acquisition is a pilot; HTTP402 remains a refusal. TEK-Torg and EAT remain unverified, without admitted identity namespaces.

Identity: source + namespace + exact external ID. Never merge distinct lot/procedure/order identifiers on numeric coincidence. Cross-platform equivalence requires separately evidenced mapping. Preserve source URI/hash, query and date range, page cursor, acquisition time and parser version in downstream immutable receipts.

Coverage: classify only the requested source/namespace/window. Verified completion requires all source pages, an exact source-reported count and equal unique observed IDs; zero requires explicit source evidence. No count, duplicate, cross-scope row, cap, incomplete page set or parse error may be promoted to complete. The helper consumes flags attested by the adapter; it does not independently verify page bytes. No complete market claim follows from complete source-window coverage.

Deployment sequence:
1. Integrate receipt validation at the GPB/SIBUR read-only snapshot boundary and replay known original snapshots. Keep legacy importers and locks unchanged.
2. Define separate typed jobs for list, detail, attachment, technical extraction, index and outcome. Require immutable source/member hashes and explicit blocked/review states. Test replay and checkpoint resume with fixtures, not production.
3. Establish source-scoped admission, mandatory backups and shared host-resource gate for every writing/heavy handler. Fresh procurement priority remains independent of historical queues.
4. Only then admit verified source-specific workers against observed source contracts. Add new source access only after actual permission and contract verification.

No live source calls, launchd changes, credentials, production DB writes, or new schedule are performed by this stage. Existing recovery task TA-FRESH-INDEX-20261120 remains open independently.

## Stage 3: isolated durable queue prototype
The SQLite prototype has six separate stages (discover, detail, attachment, extract, index, outcome), source-scoped fresh/history lanes, atomic claim and immutable job identity from source, namespace, exact notice (or discovery scope), unit SHA and input SHA. A queued historical job can be promoted to fresh; lane never changes job identity. Child enqueue requires a completed predecessor with matching source/namespace, notice when applicable, allowed stage and exact receipt SHA. Reopened ledger retains running jobs; an ambiguous write is retained in review, never retried simply because a worker stopped. Completion requires the unique attempt token and exact receipt digest and is idempotent. Sale observations cannot create downstream procurement jobs. Concurrent claims and restart verified with isolated SQLite fixtures.

Limitations: the ledger does not authenticate source bytes, prove that a discovery receipt contains a given notice, grant network/database authority, execute jobs, perform automatic reconciliation of ambiguous writes or implement production scheduling. Before connecting it to real adapters, verify parent receipt membership and artifact bytes, implement explicit safe reconciliation, timestamps/lease observation, bounded scheduler and shared admission/prewrite gates. No live queue file or runtime worker created.

## Stage 4: typed receipt and isolated recovery gate, 2026-11-21

The local SQLite queue now accepts completion **only** via a `StageReceipt` bound to the exact immutable job ID, source, namespace, stage, notice identity, input and unit digests, current attempt and parent receipt. The adapter's actual returned artifact **bytes** must match the receipt's SHA-256 and size (bounded at 64 MiB). A discovery receipt must additionally match a strict JSON membership artifact containing an exact list of IDs and an explicit empty-source flag; duplicates, wrong/foreign members, ambiguous duplicate JSON keys and arbitrary missing-original claims are rejected. All child stages retain an exact parent receipt and procurement identity. A discovery parent unlocks only IDs actually listed in its verified membership artifact.

Previously completed hash-only rows survive a backwards-compatible SQLite schema extension for audit but **cannot** authorize new child jobs without a typed receipt. Created, started and completed/review timestamps are explicit UTC values. `pending()` is limited to 32 records and never claims a job or schedules work. On interrupted attempts, `reconcile_interrupted(job_id, attempt)` idempotently moves that precise in-flight attempt to `review: interrupted_unverified`; it cannot requeue or declare success. Replaying a completed identical receipt is idempotent, while a changed receipt or wrong attempt is refused.

This is an **isolated fixture prototype only**. A typed receipt is not a signature or proof that the platform's original source is authorized, complete, legally usable, or even correctly captured: source-specific original-byte attestation, official revision membership, full-page count/coverage, legal/credential permission and privacy checks remain independent admission gates. No adapter network access, credentials, new scheduler, live DB write, ETP application, production worker cutover, retention deletion or immutable release change was performed. The next stage must apply existing MI/backup/resource controls and separately admit a source-specific writer under approved scope.
