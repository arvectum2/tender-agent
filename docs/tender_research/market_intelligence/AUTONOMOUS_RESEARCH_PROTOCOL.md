# Автономное исследование отраслевого рынка по данным закупок — протокол v1
Дата: 2026-10-27. Владелец предметной методологии: Tender Agent / Market Intelligence. Кейс: Power Quality (PQ), Россия.

## 0. Что является результатом
Один ввод пользователя должен запускать весь цикл: постановка границ -> обнаружение -> получение первичных документов -> извлечение -> отраслевой отбор -> дедупликация -> проверка итогов/договоров -> идентификация ролей -> статистика -> критическая самопроверка -> публикация. Промежуточные сообщения не являются финальным результатом. Исследование read-only; публикация заявок, платежи, отправка писем и авторизация на ЭТП не входят в автономный контур.

**Граница достоверности:** полное выполнение протокола означает проверенный охват доступных источников, а не гарантированную перепись непрозрачного рынка. Если оригинальные протоколы закрыты или не опубликованы — выдаётся итоговый отчёт с явно обозначенным неполным охватом; отсутствующие сведения не угадываются.

Для эталонного PQ-задания: Россия, 2024-10-27..2026-10-27, целевой класс 6–35 кВ. Предмет: УКРМ/конденсаторные батареи, БСК, статические и тиристорные компенсаторы, СТК/SVC, STATCOM/SVG, пассивные/активные фильтры гармоник и комплексная модернизация ПС/цехов с такими позициями. Не путать прямую поставку с проектированием, EPC, ПНР, сервисом и поставкой компонентов.

## 1. Контракт входа / выхода
Вход `ResearchBrief`: `study_id`, `question`, `geography`, `date_from`, `date_to`, `technical_scope`, `adjacent_scope`, `buyer_segments`, `source_policy`, `deliverables`, `as_of`, `language`, `budgets/limits`. Предполагаемые значения выбираются из задания и записываются; отсутствие необязательного поля не останавливает работу.

Выход:
1. `notice_register.csv` — все найденные уникальные объявления (включая исключённые с причиной); `project_register.csv` — дедуплицированные потребности; `contracts.csv` — только подтверждённые договоры и суммы;
2. `evidence.jsonl` и неизменяемый архив оригиналов с URL, датой, SHA-256, разрешением доступа и страницей/фрагментом для каждого утверждения;
3. `research_events.jsonl` — полная трасса решения и неудач, совместимая с `RESEARCH_EVENT_SCHEMA.json`;
4. `report.md` — заказчики, подрядчики/проектировщики/производители, сегменты, объёмы и цены с уровнями проверки; `coverage.json` и `quality_report.json`;
5. `training_candidates.jsonl` — примеры «вход + цитата + принятое решение + причина + статус экспертной проверки», НЕ автоматически gold labels.

## 2. Конечный автомат исследования
| Состояние | Действие агента | Выход / gate |
|---|---|---|
| S0 SCOPE | Фиксирует интервал, категорийную онтологию, исключения, метрики, критерии завершения | Замороженный brief и версия правил |
| S1 SOURCE_MAP | Строит карту ЕИС (44/223-ФЗ), реестров договоров, коммерческих ЭТП, открытых карточек/зеркал, сайтов заказчиков и OEM | Таблица доступности, приоритетов и ограничений |
| S2 DISCOVERY | Выполняет пакетный поиск по терминам, синонимам, закупщикам, EPC, площадкам и документам за каждый календарный период | Все кандидаты + query provenance + число страниц и покрытие |
| S3 ACQUIRE | Для каждого кандидата получает исходную карточку, архивы ТЗ/смет, протоколы, заключённые договоры/изменения; сохраняет хеши | Source manifest; неудачи — отдельные события, а не «нет закупок» |
| S4 EXTRACT | Data Platform распознаёт поддерживаемые форматы, текст/таблицы, делает chunks с координатами; фиксирует непарсибельные сканы | Извлечённые фрагменты с адресом доказательства |
| S5 TRIAGE | Ранжирует и классифицирует релевантность PQ на уровне **позиции внутри ТЗ**, а не только заголовка | In-scope / adjacent / false positive / unknown с цитатой |
| S6 RESOLVE | Сопоставляет номер закупки, лоты, повторные объявления, изменения и объект поставки | `notice_id` != `lot_id` != `project_id`; связи confidence |
| S7 OUTCOME | Ищет исходные итоговые протоколы/реестр договоров, идентифицирует победителя, сумму и статус | Цена НМЦ, итоговое предложение, договор отдельно |
| S8 ENTITY_GRAPH | Нормализует ИНН и связи buyer / organizer / EPC / designer / OEM / dealer / service; выделяет подтверждённую и предполагаемую роль | Entity graph; неизвестные роли остаются unknown |
| S9 METRICS | Считает рынок раздельно: прямые PQ-поставки, проектирование, EPC с выделенной PQ-частью, сервис; считает число уникальных проектов | Метрики с числителем, знаменателем, источником и coverage |
| S10 AUDIT | Независимый критический проход по всем цифрам и выборке; ищет пропуски, двойной счёт, контрпримеры | Failed checks возвращают в нужное состояние; blocker регистрируется |
| S11 PUBLISH | Создаёт воспроизводимый итоговый отчёт и пакет обучения | QA pass или честный coverage-limited result, snapshot version |

Переходы `Sx -> Sy` фиксируются в журнале событий; неудача конкретной площадки не останавливает другие площадки. После восстановления запуска продолжать с последнего durable checkpoint, не повторять проверенные артефакты.

## 3. Поиск: recall прежде precision
Не искать только «Power Quality», «FGI» или один ОКПД2. Использовать группы:
- прямые: «УКРМ», «установка компенсации реактивной мощности», «БСК», «конденсаторная установка/батарея», «фильтрокомпенсирующая установка», «ФКУ», «компенсация реактивной мощности»;
- динамические: «СТАТКОМ», «STATCOM», «SVG», «SVC», «СТК», «тиристорный компенсатор», «статический компенсатор», «регулируемый компенсатор»;
- гармоники: «фильтр гармоник», «активный фильтр», «пассивный фильтр», «АФГ», «harmonic filter», «качество электроэнергии», «провал напряжения», «несимметрия»;
- скрытые позиции: «модернизация подстанции», «реконструкция ПС», «электроснабжение ГОКа», «техническое перевооружение электропривода», «комплекс проектно-изыскательских работ», «комплектная поставка электрооборудования».

Стратегия: keyword -> расширение семантическими близкими терминами -> запросы по известным заказчикам/объектам -> поиск внутри документации широких EPC -> обратный поиск по обнаруженным EPC и поставщикам -> проверка исходных протоколов. Фиксировать каждый запрос: версия терминологии, поисковик/ЭТП, временной срез, страницы, total reported, ответ, количество уникальных кандидатов. Останавливать расширение **только после** покрытия всех запланированных типов источников/периодов и двух последовательных волн запросов без новых значимых проектных кластеров; это эвристика, не гарантия полноты.

## 4. Фильтры предмета и границы
`core_equipment`: реальная поставка/система PQ для 6–35 кВ. `core_integrated`: пакет EPC с подтверждённым PQ-оборудованием и отдельной оценкой его стоимости, если она известна. `design`: только ПИР / РД. `commissioning`: монтаж/ПНР. `service`: ремонт/ТО. `components`: компоненты PQ-системы. `adjacent`: другая ступень напряжения или неясное напряжение — показывать отдельно. `excluded`: нерелевантно.

Явно исключать фильтры воды/воздуха, «компенсацию» рабочего времени, дугогасящие реакторы при отсутствии функции PQ, общее проектирование ПС без доказанной PQ-позиции, продажи бывшего в употреблении оборудования без связи с новым спросом. При недостатке ТЗ `unknown`, а не автоматический `excluded`. Сохранить hard negatives для последующей разметки.

## 5. Дедупликация и выигранные контракты
Отдельно вести `source_record_id`, `notice_id`, `lot_id`, `project_id`, `contract_id`. Ключи-кандидаты на схлопывание: объект и подстанция, заказчик/ИНН, позиция/технические параметры, количество, период, текст ТЗ, ссылка «взамен конкурса», история отмены/повторного объявления. Совпадение слов НЕ подтверждает тождество; частичное пересечение СТК/подстанций описывать как связь частичного overlap. Журнал merge/split обязателен, плюс ссылка на основание. Отдельная сводка: сколько объявлений и сколько уникальных потребностей.

`nmck_rub`, `winning_offer_rub`, `signed_contract_rub`, `pq_equipment_component_rub`, `tax_included`, `currency`, `status` — самостоятельные поля. Не заменять договор НМЦ или ценой победного предложения. Если сумма EPC 79 млн ₽ и нет сметы по PQ, её **нельзя** включать в объём рынка PQ. Статусы «не состоялась», «отменена», «нет заявок», «договор заключён» проверять по первичным записям.

## 6. Доказательства и неопределённость
Приоритет источников для данного поля: первичный протокол/реестр договора/официальный документ -> первичная карточка ЭТП или заказчика -> отраслевой агрегатор -> сайт производителя/пресс-релиз -> аналитическая гипотеза. `source_tier` хранить для **каждого утверждения**, не только всей закупки. `A` означает проверенный первичный фрагмент; `B` — публичный вторичный источник, подлежащий проверке; `C` — гипотеза или пробел. Наличие загруженного исходного PDF не означает, что исходный итоговый протокол изучен. Сохранение SHA документа и страницы — обязательное условие обучающего gold.

Для всех существенных ячеек: `value`, `source_url`, `document_sha256`, `page_or_xpath`, `quoted_span`, `retrieved_at`, `tier`, `verification_state`, `reason`. Unknown — отдельное значение. «0», пустая строка, отсутствие ответа сервера и «не найдено в доступных источниках» — разные состояния.

## 7. Контур автономности и обработка отказов
Сеть: нормальный доступ -> разрешённый прямой/no-proxy доступ -> публичные официальные архивы -> альтернативное зеркало как secondary -> записать невозможность first-party проверки. Уважать robots, rate limits, авторизацию, лицензии, антибот и персональные данные; не обходить капчу или контроль доступа. Для временной ошибки — ограниченные retry/backoff и durable state, для 401/403/captcha — `blocked` и следующая легальная площадка. Нельзя бесконечно повторять запрос к одному URL.

Каждый период и площадка — идемпотентная очередь задач с `attempts`, `next_retry_at`, `last_http_status`, `last_error`, `raw_hash` и `completed_at`. Сохранять промежуточные результаты, даже если один провайдер упал. После перезапуска воспроизводимость должна сохраняться по `study_id`, `brief_version`, `source_snapshot` и версиям парсеров/моделей.

## 8. Контроль качества: завершение без человека
Жёсткие проверки: (a) у каждой цифры и имени победителя есть evidence; (b) суммарные стоимости не смешивают НМЦ, proposal и contract; (c) уникальные проекты посчитаны отдельно от объявлений; (d) никто не получил роль EPC/OEM/design на основании одного предположения; (e) 2024/2025/2026 проверены как самостоятельные интервалы; (f) сквозной след от вывода до исходного документа; (g) negative-search и search-coverage log заполнены; (h) срез данных/блокировки/непрочитанные PDF раскрыты; (i) аналитический вывод содержит опровергающие факты и ограничения; (j) отчёт не маскирует недоступность источника нулевым спросом.

Запуск завершён одним из исходов: `completed_verified` (достаточный документированный охват источников и все обязательные evidence-gates), `completed_with_gaps` (исследование исчерпало разрешённые способы, но имеет явно оговорённые пробелы) либо `blocked` (невозможно сформировать минимально обоснованный вывод). Уверенность в отдельных утверждениях не равна полноте рынка. Численные пороги покрытия рассчитывать и показывать: % записей с оригинальным ТЗ; % договоров с подтверждённым победителем/ценой; доступность по источникам и месяцам. Не подменять неизвестную долю произвольными «95% рынка».

## 9. Архитектурные границы
- **Data Platform:** загрузка bytes/HTML, хранение с SHA, extraction, OCR при разрешённом источнике и необходимости, chunking, индекс, semantic/lexical retrieval, generic provenance, retry/storage.
- **Tender Agent / Market Intelligence:** онтология закупок и PQ, планы запросов, источники ЕИС/ЭТП, классификация, dedup, протоколы, buyer/winner/EPC/designer, финансы, покрытие, аудит, отраслевой отчёт.
- **Procurement LLM:** inference на evidence-bounded tasks и позднее специализированный fine-tune по проверенным кейсам. Не источник истины и не заменяет оригинал протокола.
- **Arvectum OS:** задачи, расписания, права, артефакты, оповещения; не дублирует procurement-правила.

Существующий `docs/tender_research/free_web_research_pipeline.md` — часть acquisition; это **не** готовая end-to-end research автоматика. Существующая граница `docs/tender_research/data_platform_boundary.md` сохраняется.

## 10. Разметка и обучающий цикл
От каждого смыслового решения писать event: исходный запрос/кандидат, document hash + span, решение, альтернативные гипотезы, правило, reason, статус проверки и применённую версию модели. Логировать и полезные отрицательные примеры. Пример `training_eligible=true` допустим **только** после сохранения лицензируемого источника, source span, корректной категории, контроля утечки данных и независимой проверки метки. До этого лог служит только как candidate dataset.

Типы будущих задач LLM: `pq_relevance`, `document_requirement_extraction`, `entity_role_linking`, `award_extraction`, `same_project_dedup`, `mixed_epc_cost_allocation`, `citation_sufficiency`, `contradiction_detection`. Выборку train/val/test делить по проектным группам, покупателям и времени, а не случайно по строкам/повторным объявлениям. Замораживать test-set; сравнивать с lexical+rules baseline; критерии — precision/recall, F1 по категориям, provenance accuracy, hallucination rate, financial error rate. Не обучать модель на собственных неподтверждённых генерациях.

## 11. Реализация от документа к автономному продукту
P0: event/evidence schemas, durability, search-coverage registry, read-only trace и воспроизводимые тестовые кейсы.
P1: соединить источники и Data Platform; полнота/динамическое расширение запросов, source fallbacks, оригинальные протоколы; не использовать демо как реальные результаты.
P2: classification/dedup/contract/entity graph; golden casepack со сложными EPC и повторами.
P3: QA gates, независимый adversarial review, автономная публикация отчёта и exit reason.
P4: режим «один запрос -> одно полное исследование» с checkpoint/resume, мониторинг, затем запуск benchmark и только после этого обучение Procurement LLM.

**Текущий статус:** протокол и пример корпуса документируют требования. Работающий автоматический оркестратор S0..S11 этим документом **не создан**. Сверять реализацию с данным протоколом, а не считать описание доказательством готовности.
