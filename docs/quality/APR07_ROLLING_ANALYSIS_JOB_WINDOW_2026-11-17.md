# APR-07 — измерение скользящего окна заданий анализа

Разработан read-only измеритель в существующем `ops_observability`: `measure_analysis_window(session, now=..., days=7)`. Вызывать только из авторизованного операторского процесса с отдельно разрешённой SQLAlchemy Session (для проверки использовалась изолированная тестовая БД). Новая публичная ручка сознательно не открыта, прежний контракт `/api/ops/observability` не изменён. Нет записи в БД, загрузки моделей, сетевых вызовов или переключения конфигурации.

Окно `[now-days, now)` в UTC, целые 1–30 дней. В выборку попадают только существующие строки `TenderAnalysisJob` типа `analyze` с финальным временем и статусом completed / completed_with_warnings / failed / cancelled. Это срез текущих строк, **не журнал неизменяемых событий**: повторные попытки и отменённые/перезаписанные истории не восстанавливаются. `clean_completion_rate` — доля строк со статусом completed среди четырёх финальных исходов, а не точность отчёта. Неполные timestamps, отсутствие finish и переполнение лимита 10 000 выводятся отдельно; усечённый агрегат не выдаётся. P50/P95 nearest-rank по `finished_at-created_at` только завершённых/завершённых с предупреждениями задач с корректным порядком created≤started≤finished. Это время от создания задания до завершения с ожиданием очереди, а не полное ingestion-to-report и не time-to-human-decision. Порог 100 валидных строк — предварительный минимум для измерения, **не утверждённый SLO**. Даже при достаточной выборке статус OBSERVED_NOT_APPROVED. Для неизвестного знаменателя — null. Исторические модельные времена APR-06 не импортируются в этот срез.

Инженерная проверка проводится на синтетических данных; реальные rolling SLO измерять только в согласованном staging/production-like окне с достаточной выборкой и проверкой событий/tenant scope. Не считать отсутствие ошибок или наличие completed эквивалентом commercial acceptance.

## Локальный операторский запуск

`python -m scripts.ops.apr07_analysis_window --days 7` читает только явно заданную переменную `AI_CORP_APR07_READONLY_DATABASE_URL`. Требуется PostgreSQL+psycopg через локальный Unix socket и отдельный непривилегированный LOGIN, которому выданы SELECT только на `job_type,status,created_at,started_at,finished_at,updated_at` таблицы `public.tender_analysis_jobs`. Не использовать SaaS-admin, общую прикладную роль или production DSN без отдельного разрешения. Не передавать секреты командной строкой; конфигурация остаётся у оператора. При отсутствии DSN, неразрешённой роли/записи, ошибке соединения — exit 2 без вывода секретов. Транзакция REPEATABLE READ READ ONLY, ограничение времени запроса 15s. Старый HTTP API не изменён.

Воспроизведение на отдельном локальном PostgreSQL: `python -m scripts.acceptance.run_apr07_operator_postgres`. Временный Unix socket без TCP, фактическая таблица модели, 100 синтетических записей, P95 95 секунд, отказ владельцу и пишущей роли, проверка SELECT закрытого поля и UPDATE, контроль сохранности строк и штатное удаление кластера. Реальные рабочие данные не использовались. На macOS для initdb/pg_ctl установлен LC_ALL=C, иначе наблюдалась ошибка запуска postmaster, исправленная без изменения системных настроек.

### Проверка границ чтения после интеграции

CLI дополнительно требует фактически читаемые ровно шесть разрешённых пользовательских столбцов таблицы. Полный SELECT, лишний SELECT из наследуемой роли, отсутствие хотя бы одного необходимого столбца и включённый RLS отклоняются до вычисления метрик. Это проверка эффективных прав на конкретную таблицу, а не сертификация всех прав роли в БД. Обычная таблица без RLS необходима для заявленной общесистемной области измерения; при иной архитектуре нужен отдельный tenant-aware контракт. PostgreSQL acceptance повторно подтвердил успешный расчёт 100 синтетических строк, P95=95 секунд, отказ пяти неподходящим ролям и отказ при RLS. Публичный HTTP API и рабочая БД не изменялись.
